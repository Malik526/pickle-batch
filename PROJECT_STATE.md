## Current Architecture

Three cooperating CLIs share one SQLite database (`data/content.db`, gitignored):

- `generate_calendar.py` — generates a month of posts from a configurable posting cadence (`scheduling.py`), pushes them to Google Calendar, and persists one `content_slots` row per event. In the default `fifo` routing mode, every slot is untyped (`pillar_key = NULL`, no allocation). In `pillar` mode, weighted pillar allocation assigns a `pillar_key` per slot, as before.
- `process_content.py` — discovers `.mov`/`.mp4` files in `content/incoming/`, inspects/transcribes each, derives a caption candidate, and (in `pillar` mode only) classifies, then assigns the video to the earliest matching open `content_slots` row.
- `publish_tiktok.py` (Milestone 2.0) — manually publishes one already-assigned video to TikTok and persists the result in `platform_posts`. Not chained to the other two automatically — see "TikTok Publishing" below.

Google Calendar remains the human-facing source of truth for the schedule; `content_slots` is an internal mirror `process_content.py` queries and claims. See `docs/decisions/0001-video-ingestion-pipeline.md`, `docs/decisions/0002-configurable-cadence-and-weighted-pillar-allocation.md`, `docs/decisions/0003-local-embedding-classification.md`, `docs/decisions/0004-dedicated-google-calendar-ownership.md`, `docs/decisions/0005-fifo-baseline-and-optional-strategy-routing.md`, and `docs/decisions/0006-tiktok-publisher-foundation.md` for the full rationale.

The default `process_content.py` pipeline is fully local and requires no API key: ffmpeg + faster-whisper + SQLite, and (only in `pillar` mode) local embedding classification (`fastembed` + `BAAI/bge-small-en-v1.5`). Claude remains available as an optional classifier (`config.CLASSIFIER=claude`, pillar mode only) for comparison/benchmarking via `evaluate_classifier.py`.

## Routing Strategy (Milestone 1.3)

`config.ROUTING_MODE` (`CONTENT_CALENDAR_ROUTING_MODE`, default **`"fifo"`**) is an explicit, separately validated setting — never inferred from whether `CONTENT_TYPES` is populated. `scheduling.validate_routing_mode()` fails immediately and clearly on any other value.

- **`fifo`** — the default V1 automation path. No pillar or classifier is required or invoked: `generate_calendar.build_schedule()` produces untyped `OPEN` slots straight from the posting cadence and the future-only filter, and `process_content.py` never constructs a `ContentClassifier` in this mode at all (so an invalid/unset `CONTENT_CALENDAR_CLASSIFIER` cannot block it, and no embedding-model load cost is paid). Matching is `slot_matcher.select_slot_fifo`: earliest `OPEN` slot at/after now (inclusive), ingestion order, no pillar filter.
- **`pillar`** — the original Milestone 1/1.1/1.2 strategy, fully preserved and regression-tested: weighted allocation at generation time, classify → confidence gate → pillar-specific slot match at ingestion time. See "Active Pillar Strategy" below.

**Transcription is decoupled from scheduling in `fifo` mode only.** Media validity (ffprobe passes, audio stream exists) is still a hard precondition in both modes. But if `faster-whisper` itself fails on an already-valid video: in `fifo` mode the video is still scheduled (`videos.status="TRANSCRIPTION_FAILED"`, `transcription_status="FAILED"`, caption falls back to `caption_source="none"`) rather than being routed to `content/failed/`; in `pillar` mode this is unchanged from before — still a hard `FAILED`, since classification has nothing to work with otherwise. See ADR-0005 for why transcription is kept *before* (not after) slot assignment in the pipeline despite being non-blocking.

**FIFO ordering.** `process_content.discover_videos()` sorts a video already known to the database (still waiting in `content/incoming/` from a prior run) by its immutable `videos.created_at`, so its position survives the file being touched or copied — but not renamed, which is treated as a new video (documented limitation, not silently broken). A genuinely new file sorts by filesystem mtime, tie-broken by filename.

## Captions (Milestone 1.3)

`videos.caption_text`/`caption_source` (nullable) are first-class metadata, populated in **both** routing modes right after the transcribe stage, governed by `config.CAPTION_MODE` (`CONTENT_CALENDAR_CAPTION_MODE`, default `"transcript_auto"`):

- `transcript_auto` — `caption.build_caption_from_transcript()` normalizes whitespace only, **no truncation** (platform-specific length limits are deferred to the eventual per-platform publisher, not baked into the canonical stored caption). Falls back to `caption_source="none"` when the transcript is permanently unavailable (`TRANSCRIPTION_FAILED`).
- `manual` — never writes `caption_text` (no editing UI exists yet); only records `caption_source="manual"` so the stage is idempotent and never overwrites a future UI's caption.
- `none` — no caption generated.

No caption approval state machine (`DRAFT`/`APPROVED`/`AUTO`) yet — deliberately deferred, would not simplify anything without a UI. No `platform_posts` table yet either — video:post stays 1:1 until TikTok publishing actually exists; see ADR-0005 for the reasoning.

**Milestone 3.10 (hosted caption editing):** the canonical `videos.caption_text` is now editable per video from the Queue (`GET`/`PUT /api/videos/{id}/caption`, `POST .../caption/generate`; `media/caption_editing.py`, `media/caption_generation.py`). `caption_source` gains `transcript_auto_edited` for generated-then-edited text. A user-cleared caption is stored as `NULL` + `manual`, so this pipeline's caption stage still never overwrites it. Regeneration needs explicit `overwrite`. The caption locks once a platform post is submitted. Publishers read it via `publishing/caption_resolution.resolve_publish_caption` (the per-platform override seam). Generation only works where a transcript exists, which today means CLI-ingested videos, not hosted uploads. See ADR-0014. **Milestone 3.10.1:** hashtags are parsed from the caption (`media/hashtags.py`) into a relational `video_hashtags` table, rewritten atomically with every caption write (`set_video_caption`, including this pipeline's `transcript_auto` step). They are internal metadata only; the caption string itself is never reformatted.

## Shofo Real-Video Evaluation Corpus (Milestone 1.3.1)

A test/evaluation utility, not a production feature — it does not change scheduling behavior. `download_shofo_samples.py` pulls a small (~12), reproducible (`--seed`), stratified sample of raw MP4s + reference metadata from the gated `Shofo/shofo-talking-head-en` Hugging Face dataset (~10k clips, ~104GB) into `evaluation/video_pipeline/` (gitignored except `README.md`) — never the full dataset, and never decoding video during row selection (`_disable_video_decoding()` disables Video-feature decoding before any row is pulled via `IterableDataset.decode(False)`, falling back to `Video(decode=False)` on older `datasets` versions — checking `ds.features` directly is unsafe, since that access peeks and decodes one row on a streaming dataset with an unresolved schema). `evaluate_transcription.py` then runs the real, production `transcription.FasterWhisperTranscriber` against each clip and reports WER/CER against the dataset's own WEBVTT reference transcript (a reference ASR output, not ground truth) plus `realtime_factor`. `transcript_metrics.py` holds the pure WEBVTT-normalization and Levenshtein-based WER/CER functions both scripts (and their tests) depend on.

**Verified real schema differs from the dataset card**: there is no `file_name` column — the downloadable reference lives inside the raw (non-decoded) `video` feature value as an `hf://datasets/<repo>@<revision>/<path>` URI, parsed by `_relative_path_from_video_field()`. `normalize_row()` is the one boundary function that translates Shofo's real field names to this project's internal manifest names (`_DIRECT_FIELD_MAP`); every other function (filtering, stratification, download, manifest) operates only on that normalized shape. Also confirmed by scanning the full metadata stream: `has_music` is `False` for all 10,000 rows in this dataset release (not a bug — the sampler's music alternation just has nothing to alternate with today). See `evaluation/video_pipeline/README.md` ("Observed Schema") for the full verified shape.

Neither script imports `content_store`, `slot_matcher`, `classification`, or `calendar_manager`. Dependencies (`datasets`, `huggingface_hub`) live in `requirements-eval.txt`, kept out of `requirements.txt` so the production dependency set is untouched.

This corpus is for media/transcription/FIFO testing only — **not** pillar-classification accuracy. The clips are arbitrary social talking-head content unrelated to `config.CONTENT_TYPES`; do not calibrate embedding thresholds or report pillar accuracy against it.

**Real acquisition and transcription benchmark now both verified live**: gated dataset access/authentication (`huggingface-cli login`/`HF_TOKEN`) was already configured in this environment, so `download_shofo_samples.py --count 1` and `--count 12 --seed 42` were both run for real against the live dataset — 12/12 downloaded, 0 failed, each a real, ffprobe-valid MP4 (see the schema-mapping fix above). `evaluate_transcription.py` was then run for real against all 12 with the actual `FasterWhisperTranscriber` (`base` model, CPU) — **12/12 transcribed with 0 errors**, mean WER **7.2%** (median 7.3%, range 0.0%-13.5%) against the dataset's WEBVTT reference transcripts, and mean `realtime_factor` **0.083** (transcription took ~8% of each clip's duration — roughly 12x faster than real-time on CPU), confirming local faster-whisper is practical for this workflow. ## TikTok Publishing (Milestone 2.0)

**Milestone 3.12:** hosted execution runs in a separate worker process (`cli/run_worker.py` → `scheduling/hosted_worker.py`), reusing this same claim/publish/retry/recovery/reconciliation machinery per hosted user with per-user credentials and timezone-exact due selection. See ADR-0015.

**Milestone 3.13:** the publish path writes a submission checkpoint (`platform_posts.submission_state`) and `TikTokPublisher` persists its `publish_id` before uploading media, so a crash or an ambiguous upload error is reconciled, never resubmitted. Crash recovery requeues a never-submitted claim, retries (bounded) one interrupted before TikTok issued an id, and parks an undeterminable one as status `UNKNOWN`. Reconciliation parks an accepted submission as `UNKNOWN` (not FAILED) when its status can't be checked or never resolves. `UNKNOWN` and `FAILED` posts are recovered only through `POST /api/queue/slots/{id}/retry`. Hosted token refresh holds a per-connection Postgres advisory lock. Hosted publish-time ffprobe metadata is persisted, and silent videos are publishable. See ADR-0016.

**Milestone 3.11:** every failure write also stores a structured `platform_posts.failure_code`. The hosted Queue's publish state and failure copy come from `publishing/publish_status.py` + `publishing/failure_taxonomy.py`. `failure_reason` remains internal diagnostic text only. See ADR-0013's 3.11 addendum.

Proves `one known local MP4 → connected TikTok test account → TikTok API → private post → poll/check result → persist publishing result` for exactly one manually-chosen video — a standalone manual CLI (`publish_tiktok.py`), deliberately **not** wired into `process_content.py`, a scheduler, or any background process yet. See `docs/decisions/0006-tiktok-publisher-foundation.md` for the full architecture and rationale; this section is current-state only.

- **New table `platform_posts`** (`content_store.py`): one row per `(video_id, platform)`, `UNIQUE(video_id, platform)` enforced by the schema — the idempotency guarantee, not just caller discipline. Statuses: `PENDING`/`PUBLISHING`/`PUBLISHED`/`FAILED`. Preserves the three-way separation from ADR-0005: `videos` = canonical content/media metadata, `content_slots` = scheduling assignment, `platform_posts` = external publishing state/result — nothing TikTok-specific was added to `videos`.
- **`publisher.py`**: platform-neutral `Publisher` interface (`publish`, `get_status`) + `build_publisher()`, mirroring the existing `Transcriber`/`ContentClassifier` interface-plus-factory pattern. Only `"tiktok"` is registered; anything else raises `UnsupportedPlatformError` immediately.
- **`tiktok_publisher.py`**: `TikTokPublisher`, the only implementation. Queries the account's real `privacy_level_options`/`max_video_post_duration_sec` via `creator_info` before ever publishing, then Content Posting API v2's `FILE_UPLOAD` flow: `init` → `PUT` raw bytes to the returned `upload_url` → `status/fetch` to poll. All TikTok-specific request/response shapes live only here. **Unaudited-client restriction** (`unaudited=True`, the default): requires `privacy_level == "SELF_ONLY"` *and* `"SELF_ONLY"` actually present in `creator_info`'s `privacy_level_options` — never falls back to another level, never treats an empty options list as "unrestricted" (`unaudited=False` preserves that older, more permissive check for a future audited client). **Caption length**: validated in UTF-16 code units (`config.TIKTOK_MAX_CAPTION_UTF16_UNITS`, 2200) — not Python `len()`, which undercounts non-BMP characters — fails with `CAPTION_TOO_LONG` rather than truncating `videos.caption_text`. **Duration**: checked against the account's own `max_video_post_duration_sec`, via `media.inspect_media()` (reused, not a second media path).
- **`tiktok_auth.py`**: TikTok OAuth, completely separate from Google Calendar's (different config vars, different cached token file at `~/.config/content-calendar/tiktok_token.json`, different scopes, no shared code). **Corrected** (2026-09-16): TikTok's current Desktop Login Kit documentation *does* support `localhost`/`127.0.0.1` redirect URIs (including a wildcard port) and mandates PKCE for desktop apps — an earlier version of this milestone assumed no useful loopback flow existed and shipped manual-only. The preferred flow, `tiktok_auth.py --authorize`, now generates a fresh PKCE `code_verifier`/`code_challenge` and a fresh cryptographically random `state` per attempt, starts a temporary localhost callback server, verifies `state` exactly before exchanging anything, and caches the token. A manual two-command fallback (`--print-auth-url` then `--exchange-code <code> --state <state>`) remains for environments where the interactive flow can't run — it also generates a fresh PKCE pair and validates `state`, transiently cached between the two commands and deleted immediately after, never persisted like the long-lived token. `get_access_token()` refreshes transparently afterward.
- **`publish_tiktok.py --video-id <id>`**: load video → verify local file exists and is TikTok-compatible (`media.is_tiktok_compatible`, reused) → verify a stored caption exists → `Publisher.publish()` (which itself validates caption length and duration before any network call) → persist `platform_post_id` immediately (before polling, so a crash between submission and polling can't lose it) → `Publisher.get_status()` → persist outcome. `--poll-only` re-checks an in-flight submission without ever submitting.
- **Idempotency rule**: once `platform_post_id` is set for a `(video, platform)`, `publish()` is never called again under any circumstance — including a `FAILED` status, which is a distinct case ("TikTok accepted it, then reported failure") from a true submission failure (`platform_post_id` still `None` — safe to retry, reuses the same row rather than inserting a second).
- **Prerequisite fix in `process_content.py`**: `videos.canonical_media_path` was set once at inspect time (the `content/incoming/` discovery path) and never updated when the file moved to `content/processed/` on assignment — silently stale for any consumer reading stored state rather than re-discovering the file, which is exactly what `publish_tiktok.py` does. `_move_file` now returns the destination path, folded into the same `update_video` call that sets `status="ASSIGNED"`. The real database's 5 already-assigned Shofo videos were repaired to match.

**Real, live verification in this environment (up to the credentials boundary)**: the PKCE + state + localhost-callback *mechanism* itself was verified with a real (non-mocked) local HTTP round trip — a background thread "clicks" the redirect URL exactly as a browser would, exercising the actual server bind, state comparison, and code/verifier exchange call. `publish_tiktok.py --video-id 1` was run for real against the actual `data/content.db` and the real (post-repair) file at `content/processed/7000056250327174406.mp4` — it correctly resolved the video, passed the file-exists/TikTok-compatible/caption-presence checks, and (during this correction pass's re-verification) caught real video 1's actual transcript-derived caption exceeding the new 2200-UTF-16-unit limit (2522 units) with `CAPTION_TOO_LONG`, persisted as `platform_posts.status=FAILED`/`platform_post_id=NULL` (safely retriable). An earlier verification pass (before the caption-length check existed) reached further and got the actionable "no TikTok credentials" error from `tiktok_auth.get_access_token()` instead. **Not verified live in this environment**: the actual TikTok Developer Portal app setup, granting this app a real registered redirect URI, the real OAuth exchange against TikTok's servers, and a real `creator_info`/`init`/upload/`status`/private-post round trip — no TikTok developer credentials or dedicated test account were available here (same constraint as ADR-0004's Google Calendar OAuth). The exact request/response shapes in `tiktok_publisher.py` are implemented from TikTok's public API documentation, not confirmed against a live call. Automated tests mock every TikTok network call (the loopback server itself is real, same-machine only).

Kept logically separate from the Python backend (own `package.json`/toolchain, no shared code, no imports either direction) but in the same repository, since both are the same product going forward.

- **Routes**: `/` (homepage), `/privacy`, `/terms` — all real, statically-exported, routable pages. No authenticated screens, uploads, billing, or dashboard — explicitly out of scope for this milestone.
- **Stack decision**: Next.js App Router + TypeScript + Tailwind CSS v4, following this session's global engineering convention for Next.js projects (`components/ui`, `components/layout`, `components/sections`, `lib/` — see `~/.agents/CODING.md`'s "Frontend And TypeScript" section) rather than inventing a new structure. Static export (`next.config.ts`: `output: "export"`, `trailingSlash: true`) — no server-rendered/dynamic routes exist yet, so no Netlify Next.js runtime plugin or serverless functions are needed; this is the "do not introduce unnecessary infrastructure" reading of the brief, not a permanent architectural ceiling — switching away from static export when `/app/*` needs real server rendering is a small, well-documented config change.
- **Design system**: provisional V1, centralized in exactly two places so it's easy to change later — `web/app/globals.css`'s `:root`/`@theme` block (background/surface/ink/border/one accent color, `#4338CA`) and `web/lib/site-config.ts` (name/tagline/description/contact email). Components reference tokens via Tailwind utility classes only — no hardcoded hex values in any component. Neutral light base, strong whitespace, one accent, no gradients/animation clutter, mobile-first (verified: viewport meta present, responsive Tailwind breakpoints throughout, a client-side mobile nav toggle in `SiteHeader`).
- **Homepage content** describes only what exists or is genuinely in progress: batch-oriented workflow, automatic scheduling, transcript generation, caption preparation, FIFO queue, and "TikTok publishing integration in development" (not "TikTok publishing" as a completed, working feature) plus a stated future-multi-platform direction (Instagram/YouTube Shorts marked "Planned"). No feature is claimed that doesn't exist in the backend today.
- **Privacy Policy / Terms of Service**: real, proportionate (not enterprise-length) pages reflecting the actual current implementation — OAuth/token storage for connected integrations, video/transcript/caption processing, no data sale, third-party (TikTok/Google) processing under their own policies, deletion-request contact path, explicit "in active development/testing" framing throughout. **`lib/site-config.ts`'s `contactEmail` (`support@content-automation.app`) is a placeholder** — must be replaced with a real, monitored address before this site is deployed publicly or submitted to TikTok, since both legal pages promise it as a real contact method.
- **Future SaaS routes** (`/app/calendar`, `/app/uploads`, `/app/settings`, `/app/integrations`) are deliberately not started, not even as placeholders — the brief for this milestone called a minimal placeholder architecturally optional, and none was judged necessary yet; the `app/` folder structure already accommodates adding them later without restructuring.

**Verified live in this environment**: `npm run build` (Next.js 16.3.5, Turbopack) compiles cleanly, `npm run lint` reports no issues, and all three routes (`/`, `/privacy`, `/terms`, plus the default `/_not-found`) export as static HTML. The static `out/` output was served locally (`python3 -m http.server`) and checked directly: all three real routes return HTTP 200 with correct titles/content, footer links resolve to `/privacy/`/`/terms/`, the CTA/contact `mailto:` links render correctly, and a nonexistent path correctly returns 404. **Not verified live**: an actual Netlify deployment (no Netlify account/site was created in this environment) — the `netlify.toml` config, build command, and publish directory are correct per Next.js's own documented static-export/Netlify guidance, but the real deployed URLs have not been confirmed to work end-to-end. That, and replacing the placeholder contact email, are the user's remaining manual steps before using the resulting URLs in TikTok Developer Portal configuration.

No ADR added — the stack/structure choices here follow existing global conventions directly (see "Stack decision" above) rather than introducing a new durable architectural decision specific to this repository.

**Milestone 3.15 (functional UX, client state, native prep):** the `/app` shell now keeps server state in one TanStack Query cache (`web/lib/query/`, `web/hooks/`), provided by the persistent `/app` layout, so revisiting a screen renders from cache while stale data refreshes in the background. Mutations update or invalidate exactly the affected entries (e.g. a Queue assignment refreshes both the Queue and the Library's `publish_status`). Navigation-worthy UI state (Library filter, Queue view/month, unsaved cadence draft) lives in memory via `web/lib/ui-state.tsx`. The cache and UI state are user-scoped and dropped on sign-out or an account switch. Measured in a browser with a 400 ms fixture API, revisits went from ~810 ms with a spinner to ~45 ms with none, and one walk around the app from 27 requests to 4. No backend change. See ADR-0017, `docs/evaluations/productization/milestone-3.15-functional-ux-native-prep.md`, and `docs/architecture/native-ios-readiness.md` (iOS-first native plan; the backend is already client-neutral for auth; the TikTok OAuth return target and native upload adapter are the documented Milestone 7 changes).

**Milestone 4.0 (Instagram integration foundation):** Instagram uses the Instagram API with Instagram Login: professional Business/Creator accounts, no Facebook Page, scopes `instagram_business_basic` + `instagram_business_content_publish` (verified against Meta's docs 2026-10-04). It fits the existing platform-generic tables (no Instagram-specific tables). Built:
- a platform registry with a minimal capability model (`publishing/platforms.py`);
- the Instagram config contract and validation (`publishing/instagram/configuration.py`, `.env.example`);
- `StorageProtocol.create_signed_url`, short-lived signed URLs to private media, verified against the real bucket, which stays private;
- a guard so the materializer only creates posts for platforms with a hosted publisher;
- a read-only `GET /api/platforms/instagram/status`;
- an Instagram card in Settings (real status, no Connect yet).

The publishing lifecycle (container → status → `media_publish`) is mapped onto the 3.13 checkpoint and UNKNOWN rules in ADR-0018; the generic changes it needs (media-source publisher input, finalize step, `platform_media_id`) are 4.2 work. Next: 4.1 Instagram OAuth after the Meta app is set up (checklist in `docs/evaluations/productization/milestone-4.0-instagram-foundation.md`).

**Milestone 4.2 (Instagram Reels publishing):** implemented through the existing claim / checkpoint / reconciliation / recovery machinery, with no Instagram tables. Container creation from a short-lived signed URL (the bucket stays private), the container id kept in `platform_post_id`, status checks, and a single `media_publish` path (`scheduling/finalization.py`) behind a `PUBLISH_REQUESTED` checkpoint. The Reel id is stored in the new `platform_posts.platform_media_id` (migration `0012`). Ambiguous publishes are resolved from container status and never re-published automatically. Reels media and caption limits are validated before any Meta call; 4K uploads are rejected, with no transcoding. The worker dispatches by platform. Queue assignment accepts a `platforms` choice, and the Queue shows per-platform delivery (Processing / Publishing / …). Mocked-Meta tests pass on SQLite and Postgres, and live signed-URL delivery is verified. **Live Reel publication awaits a deploy of both services**, because opening a store applies `0012` and pre-4.2 code can't read the new column. See `docs/evaluations/productization/milestone-4.2-instagram-reels-publishing.md` (includes the 2026-10-10 accidental-migration incident and its rollback).
